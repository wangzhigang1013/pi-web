# Preview Annotations for Markdown and Source Views

## Context

Users reviewing plans, documents, and code generated by AI coding agents often need
to provide targeted feedback on specific paragraphs, sentences, or line ranges.
Communicating these revisions through natural-language chat (e.g. "in paragraph 3, change X to Y")
is error-prone, ambiguous, and slows down iterative refinement.

Coding assistants such as OpenAI Codex (in the desktop client) provide inline annotation
mechanisms directly on rendered previews and code views, allowing users to select
text, attach actionable notes, and batch-submit them for in-place source modification.

Pi Web previously lacked any visual annotation capabilities. Pi package extensions
operate in an RPC sub-protocol limited to dialogs and plain-text widgets, with no
frontend injection slot for rendered preview views (`docs/rpc-extension-ui.md`).

## Decision

We introduce an integrated **Preview Annotations** subsystem in Pi Web, covering
Markdown previews and source code views in the initial iteration (M1).

### 1. Dual-Anchor Strategy (Line Range + Quote Selector)
- **Primary Anchor**: 1-based source line range (`startLine`, `endLine`).
  - Markdown preview blocks are annotated with `data-src-start` and `data-src-end`
    attributes via an in-pipeline `rehypeSourceLines` plugin placed after `rehypeSanitize`.
  - Source code view lines already carry `data-line-number` attributes.
- **Secondary Anchor**: W3C-style quote snapshot (`quote`, `prefix`, `suffix`)
  extracted by `lib/annotation-anchor.ts`.
  - If a file is edited externally, the line range may drift; the quote anchor
    allows the client to relocate the annotation or signal that the target text was deleted.

### 2. Isolated Storage (localStorage)
- Annotations are stored in `localStorage` keyed by `pi-web:annotations:<sessionId>:<filePath>`.
- The source document on disk is never polluted with synthetic comment tags (such as HTML comments),
  preserving pristine files for version control and other tooling.
- Annotations survive page refreshes, tab closures, and session switches.

### 3. Batched Submission Pipeline (`submitText`)
- Instead of firing a new turn for every single note, notes accumulate into a
  per-file pending list displayed in a floating toolbar at the bottom of the viewer.
- Clicking **Send N Annotations** compiles a structured, prompt-engineered checklist:
  - Relative file path and line numbers;
  - Exact quoted block with surrounding context;
  - Explicit instruction to edit targeted sections in place rather than regenerating the full file.
- `ChatInputHandle` is augmented with `submitText(text)`.
  - If the agent is idle, the prompt is dispatched immediately via `onSend`.
  - If a stream or tool turn is active (`isStreaming`), the prompt is seamlessly queued
    as a `followUp` message to avoid dropping user input.

### 4. Modular Separation & Upstream Maintainability
To minimize merge conflicts against upstream `agegr/pi-web`:
- Core state machine, persistence, and prompt formatting live in `lib/annotations.ts`.
- Selection snapshotting, context enrichment, and quote relocation live in `lib/annotation-anchor.ts`.
- UI overlay, floating selection marker, composer, and drawer live in `components/PreviewAnnotations.tsx`.
- `FileViewer.tsx`, `ChatInput.tsx`, and `AppShell.tsx` only receive lightweight mount points and dispatch callbacks.

## Consequences

- Users can highlight text in rendered Markdown or source lines, press **Annotate**,
  describe changes, and submit a review batch directly to the agent.
- `data.truncated` files (>256KB) automatically disable the annotation marker to prevent
  submitting stale offsets against partial documents.
- The pipeline is prepared for HTML preview annotations (M2, using an opaque-origin iframe bridge)
  and rich document export (M3).
